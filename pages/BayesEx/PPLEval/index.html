Aligning models in different PPLs


Say you have a model in Stan, or PyMC. Maybe this "model" is multiple models in a trenchcoat — something like a few thousand lines and a few dozen if statements. You've heard of something cool in another PPL. Or maybe you want to see what the corresponding syntax would look like, or how fast it would run. It's probably not worth it to port your codebase over to check, but an LLM might be pretty good at this job. LLMs are best when they have a verifiable test harness — some ability to check their work against a source of truth. I think an underdiscussed part of the math / coding apocalypse is the ability for models to check against a source of truth at inference time, not just during post-training, e.g. against tests/compilers (coding) or Lean (math). This probably has implications for AI timelines in biology, AI research, materials science, computational statistics, where verification can be longer than "instant". Statistical modelling is a little squishy, so in many cases, we can't get nearly as good a certificate of correctness. In this case, however, we can.


The basic idea


Consider eight-schools (non-centred edition): Dan Simpson might not like 8schools, but I'm using it here because: (1) I love a classic, (2) it has a constrained parameter and a transformed parameter, (3) lazy.

τ∼HalfCauchy(0,5)μ∼N(0,5)zj∼N(0,1)θj=μ+τzjyj∼N(θj,σj)
\begin{aligned}
\tau &\sim \text{HalfCauchy}(0, 5) \\
\mu &\sim \mathcal{N}(0, 5) \\

\theta_j &= \mu + \tau z_j \\

\end{aligned}

We can implement this in a few PPLs: Stan model taken from posteriordb.




  

    
    
    
  

  



@model function eight_schools_noncentered(J, y, sigma)
    tau ~ truncated(Cauchy(0, 5); lower = 0)
    mu ~ Normal(0, 5)
    theta_trans ~ MvNormal(zeros(J), I)
    theta := mu .+ tau .* theta_trans
    y ~ MvNormal(theta, Diagonal(sigma .^ 2))
end


  

  



data {
  int<lower=0> J; // number of schools
  array[J] real y; // estimated treatment
  array[J] real<lower=0> sigma; // std of estimated effect
}
parameters {
  vector[J] theta_trans; // transformation of theta
  real mu; // hyper-parameter of mean
  real<lower=0> tau; // hyper-parameter of sd
}
transformed parameters {
  vector[J] theta;
  // original theta
  theta = theta_trans * tau + mu;
}
model {
  theta_trans ~ normal(0, 1);
  y ~ normal(theta, sigma);
  mu ~ normal(0, 5); // a non-informative prior
  tau ~ cauchy(0, 5);
}


  

  



def eight_schools_noncentered(J, sigma, y=None):
    tau = numpyro.sample("tau", dist.HalfCauchy(5.0))
    mu = numpyro.sample("mu", dist.Normal(0.0, 5.0))
    with numpyro.plate("school", J):
        theta_trans = numpyro.sample("theta_trans", dist.Normal(0.0, 1.0))
        theta = numpyro.deterministic("theta", mu + tau * theta_trans)
        numpyro.sample("y", dist.Normal(theta, sigma), obs=y)


  





Are these implementations the same? What does it mean for implementations to be "the same"? Some PPLs work differently, but all of the above allow us to evaluate the joint log density of the sampled parameters Ψ\PsiΨ and data yyy:

log⁡p(Ψ,y)=log⁡p(τ)+log⁡p(μ)+∑jlog⁡p(zj)⏟prior+∑jlog⁡p(yj∣θj,σj)⏟likelihood
\log p(\Psi, y) = \underbrace{\log p(\tau) + \log p(\mu) + \sum_j \log p(z_j)}_{\text{prior}} + \underbrace{\sum_j \log p(y_j \mid \theta_j, \sigma_j)}_{\text{likelihood}}
logp(Ψ,y)=priorlogp(τ)+logp(μ)+j∑​logp(zj​)​​+likelihoodj∑​logp(yj​∣θj​,σj​)​​

Probably the most natural way to define "sameness" is to ask if the models produce the same joint log pdf — is this quantity identical up to an additive constant? This catches most implementation errors, for example, incorrect prior parameterizations, This is an easy mistake to make, even for LLMs — things like sd vs variance parameterization of the normal, shape and scale vs shape and rate for the gamma, and so on. coding errors in parameter transforms (that don't sit post-likelihood in the DAG), and so on.


Accepting this definition of "sameness", we can compute the difference in log densities between implementations at some test points Ψ\PsiΨ, and if the spread of the difference is small enough across test points, we can declare the implementations identical, at least insofar as they define the same joint log density. Other differences can still exist, some of which I'll discuss in more detail below. As an example, this does nothing to check pushforwards of the sampled parameters, e.g. generated quantities in Stan.


That is, we accept that two implementations are the same if, for a set of differences, 

di=log⁡pPPL1(Ψi,y)−log⁡pPPL2(Ψi,y),
d_i = \log p_{\text{PPL}_1}(\Psi_i, y) - \log p_{\text{PPL}_2}(\Psi_i, y),
di​=logpPPL1​​(Ψi​,y)−logpPPL2​​(Ψi​,y),

where both log densities expect constrained points, This is not actually the case, which we will discuss in a moment. we come in under the following tolerance:

max⁡i∣di−median⁡(d)∣max⁡ ⁣(1, ∣log⁡pPPL2(Ψi,y)∣)<10−8 or so
\max_i \frac{\lvert d_i - \operatorname{median}(d) \rvert}{\max\!\big(1,\ \lvert \log p_{\text{PPL}_2}(\Psi_i, y) \rvert\big)} < 10^{-8} \text{ or so}
imax​max(1, ∣logpPPL2​​(Ψi​,y)∣)∣di​−median(d)∣​<10−8 or so

Why this metric? Well, different PPLs compute slightly different things when they hand you "the log density". This is an implementation detail; some (Stan) will expect, by default, samples after their internal bijections f(Ψ)f(\Psi)f(Ψ) into Rd\mathbb R^dRd, and some (Stan) drop constants from the log density, and some don't. The second point is what we're correcting for here.


When one PPL drops constants from the log density and another doesn't, the differences at some test points will be spread — because of numerical error — tightly around some arbitrary real number, not zero. So we check that the largest deviation from the median difference is small, instead of the largest deviation from zero.


A quick note on the internal bijections thing:


Different PPLs use different internal mappings into Rd\mathbb R^dRd


For this to work, we need to be sure that, say, the log density method for Turing (logjoint(model, params)) and the log density method for BridgeStan (log_density(model, q)) are doing the same thing. Why might this not be the case? Well, we usually define the model on some constrained subspace of Rd\mathbb R^dRd, but we'd like the sampler to move over all of Rd\mathbb R^dRd, because otherwise the geometry can get wonky. PPLs handle this mostly under the hood for us, defining their own bijectors that map constrained random variables to unconstrained space, and map samples back.


Stan, by default, expects unconstrained points to be passed into the log density. Most other PPLs expect constrained points. So we need to either force Stan to accept constrained points, or hit our constrained points with Stan's bijector to push them to the space Stan is expecting. Different languages can use different transforms, complicating the problem:

The other complexity here comes from the Jacobian correction. As a quick refresher, in the post, we've been talking about mapping some constrained space to Rd\mathbb R^dRd. But the model isn't just a "space", it's an "allocation of probability over that space". Given the simplex, we have some measure — uniform, Dirichlet, etc. — that defines how probability mass is distributed over the constrained space. When we want to sample in the unconstrained space, we need to ensure that the distribution of probability mass in this new space is equivalent to the distribution in the old space. Otherwise we'll get distortions when mapping the points back for interpretation. To align the probability mass allocation when sampling, we multiply by the Jacobian correction.








BridgeStan, which takes in unconstrained points, allows us the option of seeing either log⁡p(Ψ,y)\log p(\Psi, y)logp(Ψ,y) or log⁡p(Ψ,y)+log⁡∣det⁡Jf−1(f(Ψ))∣\log p(\Psi, y) + \log \lvert \det J_{f^{-1}}\big(f(\Psi)\big) \rvertlogp(Ψ,y)+log∣detJf−1​(f(Ψ))∣ when evaluating log_density(model, q). By default, this includes the Jacobian adjustment. This will also mess with our comparison; log⁡p(Ψ,y)\log p(\Psi, y)logp(Ψ,y) and log⁡p(Ψ,y)+log⁡∣det⁡Jf−1(f(Ψ))∣\log p(\Psi, y) + \log \lvert \det J_{f^{-1}}\big(f(\Psi)\big) \rvertlogp(Ψ,y)+log∣detJf−1​(f(Ψ))∣ differ by a non-constant term, so we can't compare them. The Jacobian adjustment also depends on the specific bijection chosen, so we should turn that off for a clean comparison.


When checking alignment between PPLs, the most important component is understanding what the log_density function is actually doing, and then ensuring you set things up so that it expects the same (constrained) points and does not include a Jacobian correction. I don't know of any languages that force you to include the Jacobian correction or fail to supply an unconstrain(.) function, but if they exist, they'd be pretty annoying to work with.


What can't this check?


It's possible to get the "same model" in some sense while returning a different log density. And it's possible to get a "different model", in a sense, with the same log density. As an example of the latter case, consider a model which has the same model blocks, but contains different — perhaps flawed — pushforwards of those parameters, e.g. in Stan's generated quantities. This can actually be pretty consequential — imagine a model that marginalizes or pseudo-marginalizes out most of its latent parameters; messing up the GQ step here can totally ruin the model results, and ensuring matching log densities does nothing to help here.


In the other direction, many optimizations we'd like to make to models return different log densities. Marginalization or conjugacy tricks are one example here — anything that changes the sampled dims will trip this method up — but also many approximate methods (e.g. low-rank representations of nonparametrics) can have different log densities while being, in some sense, "basically the same model".


This is potentially problematic if log density equality is intended to be used as a target for optimizations within a PPL (e.g. taking a Stan model and making it "fast" via LLM iteration).
